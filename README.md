# RAG Knowledge Assistant

Question answering over your own documents, built with **FastAPI + PostgreSQL (pgvector)**. Documents are chunked, embedded and stored; questions retrieve the closest chunks by cosine similarity, and the answer cites the passages it came from.

Live demo: **https://rag-knowledge-assistant-97k8.onrender.com** (`/docs` for the API explorer)

## How it works

```
POST /documents ──> chunk (paragraph/sentence aware, overlapping)
                      └─> embed (hash | openai) ──> PostgreSQL: documents + chunks(vector 384, HNSW index)

POST /query ──> embed question ──> top-k by cosine distance (pgvector)
                  └─> answer: Claude over the retrieved passages, or the best passage if no key is set
                      └─> response includes sources with scores
```

Ingestion writes the document and all its chunks in **one transaction**, so a failed embedding or insert never leaves a half-indexed document.

## API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/documents` | Ingest `{title, text}` |
| POST | `/documents/upload` | Ingest a UTF-8 `.txt`/`.md` file |
| GET | `/documents` | List documents with chunk counts |
| DELETE | `/documents/{id}` | Remove a document and its chunks |
| POST | `/query` | `{question, top_k}` → answer + sources |
| GET | `/health`, `/ready` | Liveness / database readiness |

```bash
curl -X POST localhost:8000/query -H "Content-Type: application/json" \
  -d '{"question": "How do I verify the webhook signature?"}'
```

A web UI is served at `/`: drag-and-drop multi-file upload, per-document Delete, Delete all, and (in Docker) a one-click "Load sample docs".

## Run locally

```bash
docker compose up --build
# open http://localhost:8000, then load the sample docs:
for f in data/sample/*.md; do
  curl -s -X POST localhost:8000/documents/upload -F "file=@$f"; echo
done
```

## Embedding and answer modes

| Setting | Behaviour |
|---|---|
| `EMBEDDING_PROVIDER=hash` (default) | Offline, deterministic feature hashing of words and bigrams. A lexical baseline: no keys or model downloads, used for tests, CI and the free demo. |
| `EMBEDDING_PROVIDER=openai` + `OPENAI_API_KEY` | Semantic embeddings (requested at 384 dimensions to match the schema). |
| `ANTHROPIC_API_KEY` set | Answers are generated by Claude from the retrieved passages (`LLM_MODEL`). |
| no `ANTHROPIC_API_KEY` | Extractive mode: the top passage is returned as the answer. |

The OpenAI and Anthropic calls are plain HTTP and are not exercised in CI (no secrets there). Test them once with your own keys. If you switch embedding provider, re-ingest your documents: vectors from different providers are not comparable.

## Evaluation

`python -m eval.run` ingests `data/sample`, runs the questions in `eval/cases.json` through retrieval, and reports hit@1, hit@3 and MRR. CI fails if hit@3 falls below 0.85.

Baseline with the hash embedder (15 questions, 3 documents):

```
hit@1=0.93  hit@3=0.93  MRR=0.93
MISS: How do I stop attackers from replaying captured notification requests?
```

The miss is a pure paraphrase ("notification requests" vs "webhook"), which is the case lexical matching cannot solve. Run the same command with `EMBEDDING_PROVIDER=openai` to compare. This is a small set, so treat it as a regression check rather than a benchmark.

## Tests

Unit tests for chunking and the hash embedder, plus API integration tests against real PostgreSQL with pgvector (ingest, retrieve, ranking, delete cascade, validation, upload).

```bash
export TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/rag_test
pytest -q
```

## Deployment

`render.yaml` defines a Docker web service plus managed PostgreSQL. On each push to `main`, GitHub Actions runs lint, tests and the eval, builds the image, then triggers a Render deploy via the `RENDER_DEPLOY_HOOK_URL` repository secret. The schema (`CREATE EXTENSION vector` and tables) is created on startup. Check that your Render database plan allows the `vector` extension.

## Limitations

- No authentication, rate limiting or per-user document isolation.
- Plain-text and markdown only (no PDF parsing).
- Chunking is character-based, not token-based.
- Documents are matched by title: re-ingesting a title replaces the old copy.
- No hybrid (keyword + vector) search or reranking.
- Schema is created with `IF NOT EXISTS` on startup, not versioned migrations.
